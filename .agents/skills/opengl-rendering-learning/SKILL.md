# OpenGL Rendering Learning

## 적용 범위와 경로 기준

- 저장소 루트는 이 `SKILL.md`에서 세 디렉터리 위에 있는 `OpenGL-26-2`이다. 저장소 내부의 모든 과제와 하위 프로젝트에 적용하고 저장소 밖에는 적용하지 않는다.
- 스킬과 로그는 `.agents/skills/opengl-rendering-learning/` 아래에서 함께 관리한다. 상위 OpenGL 폴더에 별도 사본을 만들지 않는다.
- 문서의 프로젝트 파일 경로와 graphify 분석·산출물 경로는 저장소 루트를 기준으로 해석한다. 현재 작업 디렉터리가 하위 프로젝트라면 루트를 먼저 확인한다.

## 목표

이 폴더의 작업을 대신 끝내는 데 그치지 말고, 사용자가 다음을 스스로 설명하고 적용할 수 있게 한다.

- C++ 기초부터 OOP, DOD/ECS, STL 활용까지 프로그램 구조와 데이터 흐름을 단계적으로 설계하는 방법
- 그래픽스 구현에 필요한 컴퓨터과학 및 게임수학 개념과 코드 사이의 관계
- C++ 코드의 데이터와 수명이 OpenGL 객체 및 GPU 작업과 어떻게 연결되는지
- 한 정점과 프래그먼트가 렌더링 파이프라인을 따라 어떻게 변하는지
- 화면의 증상을 어느 파이프라인 단계의 문제로 좁혀야 하는지
- 코드 수정이 파이프라인의 입력, 상태, 변환, 출력 중 무엇을 바꾸는지

이 디렉터리의 궁극적인 학습 목표는 사용자의 그래픽스 파이프라인 이해, C++·OOP·DOD/ECS·STL 활용 능력, 컴퓨터과학 및 게임수학 이해, 그래픽스 구현 역량을 함께 향상하는 것이다.

## 학습 진행

관련 요청을 받으면 다음 원칙을 필요한 만큼 적용한다.

1. 먼저 과제 문서와 관련 코드를 읽고, 현재 요청이 연결되는 파이프라인 단계와 C++ 책임을 식별한다.
2. 설명 전에 사용자의 현재 이해를 짧은 질문, 결과 예측, 코드 흐름 설명 요청 중 하나로 확인한다. 이미 답이 드러난 내용은 다시 묻지 않는다.
3. 답은 `입력 데이터 -> 상태/변환 -> 출력` 흐름으로 설명하고, 추상 개념을 현재 폴더의 실제 변수·함수·셰이더와 연결한다.
4. 정답만 제시하지 말고 사용자가 먼저 한 단계 예측하도록 유도한다. 막힌 경우에는 전체 답보다 다음 추론 단서를 먼저 제공한다.
5. 설명 뒤에는 한 개의 회상 질문이나 작은 변형 문제로 이해를 확인한다. 사용자의 답을 확인하지 못했다면 이해 완료로 기록하지 않는다.
6. 사용자가 즉시 답이나 구현을 명시적으로 요구하면 요청을 지연시키지 않는다. 결과와 함께 핵심 단계, 변경 이유, 직접 확인할 질문을 짧게 제공한다.
7. 코드는 동작을 이해할 수 있는 최소 단위부터 단계적으로 작성한다. 각 단계의 코드를 먼저 보여주고, 입력·상태/변환·출력과 새로 도입한 문법 또는 개념을 사용자의 학습에 필요한 수준으로 설명한 뒤 다음 단계로 넘어간다.

## OpenGL-26-2 단계별 작성과 완료 보고

이 절의 추가 규칙은 이 스킬이 포함된 저장소 루트와 그 하위 디렉터리의 코드 작성·수정 작업에 적용한다.

### 계획 단계

- 구현을 학습 가능한 단계로 나누고 단계 번호, 목적, 대상 파일·함수·클래스를 제시한다.
- 각 단계에서 수정·삭제할 기존 코드와 새로 작성할 코드를 모두 명시한다. 의사코드만으로 실제 변경 범위를 대신하지 않는다. 헤더, 구현 파일, 셰이더, 호출부 등 함께 변경할 부분도 포함한다.
- 각 변경을 단계와 커밋에 연결하고 사용자 승인을 받은 뒤 작성한다. 계획 밖 변경이 필요하면 대상과 이유를 추가하고 해당 변경 전에 승인받는다.
- 완료 후 graphify 분석에 필요한 그래프 생성·갱신 범위와 산출물 경로도 계획에 포함하고 승인받는다.

### 단계별 작성과 커밋

- 승인된 단계마다 코드를 제시하고 입력·상태/변환·출력과 변경 이유를 설명한 뒤 반영한다.
- 각 단계의 코드 작성을 마칠 때마다 해당 단계만 별도 커밋한다. `1 step = 1 commit`을 지키고 여러 단계를 마지막 커밋 하나로 합치지 않는다.
- 기존 사용자 변경을 보존하고 해당 단계의 변경만 선택해 스테이징한다. 같은 파일의 사용자 변경도 커밋에 섞지 않는다.
- 커밋 메시지에는 단계 번호와 변경 목적을 적고 완료 보고에 단계별 커밋 해시를 제공한다. 커밋이 막히면 원인과 미완료 상태를 밝힌다.
- 빌드와 테스트는 실행하지 않고 사용자에게 명시적으로 맡긴다. 커밋 또는 정적 확인을 빌드·실행 성공으로 보고하지 않는다.

### 코드 블록별 before / after

- 완료 후 수정·추가·삭제한 모든 코드 블록을 파일과 함수·클래스 위치별로 나누어 `before`와 `after`를 짝지어 제시한다. 대표 예시만 제시하거나 변경 코드 일부를 생략하지 않는다.
- `before`는 이번 작업 시작 시점의 실제 코드, `after`는 최종 저장된 코드로 한다. 단계 중간 코드는 별도로 표시한다.
- 새 코드는 `before: 없음`, 삭제한 코드는 `after: 없음`으로 표시하고 해당 코드를 전부 보여준다.
- 각 쌍에 변경 이유와 동작 차이를 설명한다. 보고량이 많으면 파일·단계별로 나누되 모든 변경 블록을 포함한다.

### graphify 전체 구조 요약

- 코드 작성 완료 후 `graphify` 스킬로 전체 구조를 분석한다. 현재 세션에서 제공된 스킬 목록의 graphify 경로를 사용한다. 특정 사용자 홈이나 개인 skill-library 절대경로에 의존하지 않는다. graphify는 외부 스킬 의존성이므로 저장소에 복사하지 않는다. 스킬 또는 실행 도구가 없으면 누락된 의존성을 보고하고 설치·설정 변경은 별도 승인받는다.
- `OpenGL-26-2` 전체의 실행 프로젝트와 진입점을 식별한다. 여러 `main`과 조건부 컴파일 분기는 각각 구분한다. 서로 다른 실행 프로젝트를 하나의 호출 흐름으로 합치지 않는다.
- 각 `main`부터 초기화, 객체 생성, 콜백 등록, 이벤트 루프, 입력·업데이트·렌더링 콜백 내부 호출, 자원 해제까지 탑다운으로 요약한다. 콜백 등록 순서와 프레임워크가 나중에 실행하는 조건을 구분한다.
- 함수·메서드·클래스를 정의 파일과 호출 위치에 연결한다. 관련 셰이더와 CPU → GPU 데이터 흐름도 설명한다. 클래스·파일 자체를 함수처럼 호출한다고 표현하지 않는다.
- 현재 코드와 일치하는 기존 그래프를 활용하고 없거나 오래되었으면 승인된 범위에서 graphify 절차에 따라 생성·갱신한다.
- 그래프 관계를 실제 소스와 대조하고 확인된 호출, 의존 관계, 추론을 구분한다. 호출 순서가 불명확하면 명시한다.
- graphify를 사용할 수 없으면 제한과 미완료 항목을 밝힌다. 정적 소스 요약을 graphify 결과로 보고하지 않는다.
- 완료 보고에 사용자가 수행할 빌드·테스트, 예상 결과와 관찰 지점을 명시한다.

## Modern OpenGL 설계 기준

- OpenGL 관련 설계와 코드는 Modern OpenGL의 프로그래머블 파이프라인을 기준으로 한다.
- 정점 데이터는 VAO, VBO 및 필요한 경우 EBO로 관리하고, 셰이더 프로그램을 통해 변환과 출력을 제어한다.
- `glBegin`/`glEnd`, 고정 기능 행렬 스택, 고정 기능 조명처럼 제거되었거나 폐기된 즉시 모드·고정 기능 API를 새 설계에 사용하지 않는다.
- 레거시 코드를 다룰 때는 현재 동작을 먼저 설명하고, Modern OpenGL로 옮겨야 하는 책임과 데이터 흐름을 구분한다. 사용자가 요청하지 않은 전면 재작성으로 확대하지 않는다.

## 폴더 단위 독립성

- 각 실습 프로젝트와 Standard는 해당 폴더 전체를 별도 위치에 복사해 사용할 수 있어야 한다. 공통 원본 재사용은 허용하지만 배포·빌드·실행 사본은 프로젝트 폴더 안에 둔다.
- 소스, 셰이더, 설정, 모델, 헤더, 라이브러리, 런타임 DLL의 상위·형제 폴더 참조, 개인 절대 경로, 외부 링크 의존성을 새로 만들지 않는다. 기존 배포 구조를 공통 폴더 직접 참조로 바꾸지 않는다.
- 변경 범위에는 프로젝트/속성 파일, include, 런타임 검색·복사 경로와 필요한 의존성·라이선스를 함께 포함한다. Visual Studio C++ 도구·Windows SDK·OpenGL 지원 드라이버 같은 시스템 요구는 프로젝트 파일 의존성과 구분한다.
- 완료 시 폴더 내부 참조로 반영한 파일을 보고하고, 폴더 분리 복사 후 빌드·실행 확인은 사용자에게 맡긴다. 경로 수정·파일 복사만으로 이식성 실행 검증을 완료했다고 보고하지 않는다.

## 렌더링 파이프라인 기준선

문제를 설명하거나 진단할 때 실제로 사용되는 단계만 골라 다음 기준선에 위치시킨다.

`CPU 애플리케이션/드로우 호출 -> 정점 입력(VAO/VBO/EBO) -> 정점 셰이더 -> 프리미티브 조립 -> 클리핑 -> 원근 나눗셈/NDC -> 뷰포트 변환 -> 래스터화 -> 프래그먼트 셰이더 -> 깊이·스텐실·블렌딩 -> 프레임버퍼/화면 표시`

- 테셀레이션 및 지오메트리 셰이더는 프로젝트에서 실제로 사용할 때만 끼워 넣는다.
- 좌표 변화는 필요할 때 `로컬/모델 -> 월드 -> 뷰 -> 클립 -> NDC -> 윈도우` 순서로 추적한다.
- OpenGL은 상태 머신이므로 값 자체와 그 값을 읽는 시점의 바인딩 상태를 함께 확인한다.
- 화면에 보이지 않는다는 이유만으로 프래그먼트 셰이더 문제라고 단정하지 않는다. CPU 데이터, 객체 생성과 수명, 바인딩, 드로우 호출, 좌표, 클리핑, 래스터화, 깊이/블렌딩 순으로 증거를 좁힌다.

## C++ 연결 기준

- 포인터와 참조의 유효 기간, 컨테이너 재할당, 데이터 레이아웃, 구조체 패딩, 소유권을 GPU로 전달되는 바이트와 연결해 설명한다.
- OpenGL 핸들은 C++ 객체 자체가 아니라 컨텍스트가 관리하는 리소스의 식별자임을 구분한다.
- 버퍼, 셰이더, 프로그램, 텍스처의 생성·바인딩·사용·삭제 시점을 추적한다.
- 사용자의 학습 수준에 맞춰 평범한 구조체/클래스, 반복문, 조건문, 문자열, 벡터, 스트림을 우선한다. 고급 추상화는 문제 해결에 실제로 필요할 때만 도입하고 먼저 이유를 설명한다.
- 명령 또는 상태 변경의 계약은 원자적으로 보존한다. 실패한 작업이 일부 상태만 바꾸지 않았는지 확인한다.

## 수정과 검증 경계

- 읽기·설명·진단 요청은 파일 수정으로 확대하지 않는다.
- 사용자가 명시적으로 파일 쓰기를 요청하지 않았다면 코드를 파일에 쓰지 않는다. 먼저 작성할 전체 코드를 대화에서 보여주고 학습에 필요한 설명을 제공한 뒤, 사용자 승인을 받아 파일 Write 여부를 결정한다.
- 사용자가 파일 쓰기를 명시적으로 요청했더라도 코드나 문서, 학습 로그를 만들거나 수정하기 직전에 대상 경로와 변경 범위를 밝히고 사용자 승인을 받는다.
- 빌드와 테스트는 실행하지 않는다. 사용자가 직접 확인할 명령, 예상 결과, 관찰 지점만 제시한다.
- 사실, 코드에서 확인한 내용, 추론을 구분한다. 근거가 없으면 모른다고 밝히고 로그에 확정 사실처럼 남기지 않는다.
- 이 폴더의 텍스트 파일은 UTF-8 BOM을 사용한다. Codex 인식용 `SKILL.md`만 UTF-8 BOM 없이 유지한다.

## 어려움 로그 사용

로그는 저장소 루트 기준 `.agents/skills/opengl-rendering-learning/logs/`에 둔다. 이 경로는 스킬 폴더 기준 `logs/`와 같다. 관련 코드 경로는 저장소 루트 기준 상대경로로 기록한다. 과거 로그의 외부 절대경로는 당시 증거이므로 임의로 바꾸지 않는다. 현재 요청과 관련된 로그만 읽고, 모든 로그를 매번 불러오지 않는다.

다음 중 하나가 실제 대화나 코드 작업에서 관찰됐을 때만 로그를 작성하거나 갱신한다.

- 사용자가 개념이나 코드 흐름을 잘못 설명했다.
- 같은 오류 원인을 반복해서 혼동했다.
- 결과 예측과 실제 동작이 달랐고 그 원인을 확인했다.
- 문제를 해결했지만 이해 여부가 아직 확인되지 않았다.
- 이전의 어려움을 사용자가 스스로 해결해 이해가 향상됐음을 확인했다.

일반적인 학습 목표, 모델의 추측, 단순 오타는 어려움으로 기록하지 않는다.

### 파일명

`logs/log-주제-YYYY-MM-DD.md`

- 주제는 짧고 구체적으로 쓴다. 예: `log-클립공간과-ndc-2026-09-09.md`
- 같은 날짜와 주제의 파일이 있으면 새 파일을 만들지 말고 문제-해결 쌍을 추가한다.
- 날짜가 다르면 새 파일을 만든다.

### 기록 형식

각 파일은 다음 구조를 사용한다.

```markdown
# 학습 로그: 주제

- 날짜: YYYY-MM-DD
- 관련 파이프라인 단계: 단계 또는 해당 없음
- 관련 파일: 확인한 실제 경로 또는 없음

## 문제-해결 1

### 문제

사용자가 어려워한 지점과 그것을 확인한 발언·예측·동작을 적는다.

### 원인

확인된 원인과 추론을 구분한다.

### 해결

도달한 설명, 코드 원칙 또는 수정 내용을 적는다. 미해결이면 `미해결`로 표시한다.

### 이해 확인

사용자가 스스로 설명하거나 적용한 근거를 적는다. 확인하지 못했으면 `확인 필요`로 표시한다.

### 남은 혼동과 다음 복습

남은 질문과 다음에 사용할 회상 질문 하나를 적는다.
```

로그를 기록하기 전에 사용자 승인을 받고, 기록 후에는 어떤 문제-해결 쌍을 남겼는지 알려준다. 해결되지 않은 문제를 억지로 해결된 쌍으로 만들지 않는다.

## 응답 기준

- 핵심 결론을 먼저 말하고 근거와 분석을 이어 쓴다.
- 비유는 좌표계나 병렬 처리처럼 이해에 꼭 필요할 때만 짧게 사용한다.
- 사용자가 답할 학습 질문은 한 번에 과도하게 많이 제시하지 않는다.
- 로그에서 확인한 과거 어려움은 현재 요청과 직접 관련될 때만 복습에 활용한다.
