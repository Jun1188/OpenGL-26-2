# 처음 보는 요구를 구현하는 순서

## 읽기: 명사를 바로 클래스로 만들지 않기

요구 문장에서 동사와 조건을 뽑는다. 이동/자전/공전/왕복/붙어 있음/수평 유지/선택/정지/복귀/빛의 색/시점 변경을 각각 요구 ID로 나눈다. 원자료의 키와 범위는 그대로 기록한다. 모호한 축·단계 간격·속도·정지 방식은 선택한 해석을 주석으로 명시한다.

## 설계 표

| 요구 | 입력 | 상태 | 기준 프레임 | 계산/출력 | 코드 위치 |
|---|---|---|---|---|---|
| 광원 공전 | y/Y 토글 | phase, direction, radius | 월드 또는 부모 지역 | 위치+표시+궤도 | key/update/final-sync |
| 물체 부착 | 초기화/선택 | parent, attachment | 부모 최종 월드 | childWorld | setup/controller |
| 자세 제약 | 매 프레임 | 유지할 yaw, 위치 기준 | 월드 | 위치와 자세 별도 | pose 계산 |
| 빛 반응 | m/c/재질 편집 | lighting/color/Ka/Kd/Ks/N | 동일한 월드 공간 | uniforms→fragment | CPU binding/GLSL |

## 구현의 여섯 번 통과

1. 배경·바닥·기본 도형과 카메라부터 그린다. 불확실하면 unlit/상수색으로 시작한다.
2. 부모·피벗·지역/월드 행렬을 정지 상태로 만든다. 기준점과 축을 선으로 표시한다.
3. 키를 상태 변경에 연결한다. PRESS/REPEAT/RELEASE와 토글/유지를 나눈다.
4. dt로 phase를 갱신하고 모든 관련 출력을 같은 상태에서 계산한다. 정지/반전 시 연속성을 확인한다.
5. 광원·법선·시점을 같은 공간에 맞추고 diffuse/specular를 분리한다. 셰이더 인터페이스·실제 경로를 확인한다.
6. 조건을 하나 바꿔 다시 구현한다. 부모가 움직이거나 배율이 비균등해져도 설계가 유지되는지 본다.

순정 경로는 native/main.cpp에서 직접 GL 호출을 쓴다. Standard 경로는 SceneSetup와 사용자 컨트롤러에 상태/연산을 쓰고 필요한 공통 API를 연결한다. 둘 다 다른 사물의 정답 코드를 통째로 고르는 절차가 아니다.

## 오류를 고칠 때

화면 증상을 데이터/변환/입력 상태/GPU 계약으로 분류하고 한 가지 가설만 바꾼다. 원래 코드와 예측한 변화, 사용자 실행 결과를 기록한다. '빌드 성공', '화면에 보임', '모든 요구를 충족', '다른 조건에 적용'은 서로 다른 확인이다.

## 연습 종료 점검

- 요구 ID 각각에 입력·상태·계산·출력·코드 위치가 있는가?
- 도형이 움직이는 이유를 행렬과 시간 변수로 설명할 수 있는가?
- 광원/표시/궤도/카메라가 같은 프레임의 최종 값을 사용하는가?
- 기존 문제와 다른 조건에서 직접 수정할 수 있는가?
- debugger·학습 자료·빌드 폴더를 제외한 제출 입력과 용량을 확인했는가?

실제 2차 시험 시간은 미확인이다. 자료의 25/45/60/90분은 연습용 제한시간이며 실제 시험 배점을 의미하지 않는다.
